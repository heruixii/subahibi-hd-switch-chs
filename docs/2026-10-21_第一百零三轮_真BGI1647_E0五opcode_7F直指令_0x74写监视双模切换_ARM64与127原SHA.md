# 第103轮：原BGI1.647 E0扩展五函数、主0x7F非子族与0x74写入监视两模式严格证明

## 1. 真实原Windows BGI1.647三份EXE不变与原生E0族

原版 `BGI.exe`、原 `BGI-CHS.exe`、`BGI_patch.exe` 三份原版权重各自完整 SHA-256校验通过，仅**只读解析原本机32位x86机器码、.data与原本地GPL2源码**，没有执行原EXE、修改母版或分发商用资源。

原主 opcode `0xE0` 的 handler 地址是 **0x463ED0**，在x86 `0x463EF1` 使用 `mov ecx,[eax*4+0x50F248]`，明确指向以VA `0x50F248` 开始的256项E0原生子分发表。原生可执行区合法指针仅 **5** 个：`00`、`40`、`80`、`C0`、`C2`。原GPL2 OpenBGI `opset.c` 的 **GEN_1_640** E0子族256个允许位与此完全一致，而 **GEN_1_653** 多支持 `90`、`92`、`94`、`96` 四个原BGI1.647并没有的处理函数。

原主 opcode `0x7F`（入口VA `0x47D5A0`）独立读取VM参数、处理指针和两段内容比较，并没有读取新的一字节子指令或通过256槽子分发表派发，**不可假设1.647存在“7F扩展子族”**；GPL2 GEN_1_640/1_653本身7F子族的允许子opcode数也是0。某些更晚代际新增7F子族不能应用于此原游戏。

## 2. 找到并追溯“主指令表运行时改写”的真正含义：写入监视而非剧情分支

在本机VA `0x497080`，原执行函数依一个bool-like调用参数，向原 main VM handler指针表 `0x50E320` 的八个目标槽**各写入两套不同的函数入口**，对应 opcode `0x09`、`0x0A`、`0x0C`、`0x60`、`0x61`、`0x62`、`0x6A`、`0x6F`（store/memcopy/字符串写）。原x86 VA `0x47D010` 的主 opcode `0x74` 执行 `Thread_Pop` 等价出栈，把取得的模式值传到上述0x497080；VM真正调度器 `0x4959DA` 每步间接读取主opcode函数指针。这与上游GPL2 `ops_base.c` `Opcode_WatchMode`/`SetWatchMode` 写监视所替换的八个 handler **逐项匹配**。

所以该运行时表改写是一种**调试内存写入监控机制**，不是我们想象的剧情分支、正文解码或汉化运行时状态。`watch_mode`是可选功能，即使条件值可确定，仍应保留原VM写监视的用户可触发行为。本轮找到真正调用链但没有用未验证的原PC exe执行测试。
