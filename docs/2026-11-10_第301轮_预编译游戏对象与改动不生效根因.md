# 第301轮：查清"改了源码却打不进 NRO"的根因（预编译游戏对象）

日期：2026-11-10。设备仍是 P1116，未运行。

## 一、现象

本轮按计划给 WaitText 的 `setText` 槽（`WaitTextRich_SetText`）加了 GBK 判定与 `P1462 SETTEXT` 诊断，p1286 的 WAITOBJ 确实重编了（SHA `65a9a5e9…` → `bbc01904…`），但**最终 NRO SHA 与 P1116 完全相同**（`ae5d2b73…`）。也就是说这次改动没有进入链接。

## 二、根因

在全部 1,909 个 `.o` 里扫描特征字符串：

| 字符串 | 命中对象 |
|---|---|
| `P1036 CHS_TEXT`（真机日志里实际出现的 WaitText 诊断） | `P1432_.../P1130_GAME_ONLY_GC_AARCH64.o`、`P1130_GAME_ONLY_HOS_RELRO_AARCH64.o` |
| `P1057_ACTUAL_RUNNING_NRO` | 同上，另有 `P1382_.../p1382_P1057_..._AARCH64.o` |
| `P1461 BMPTEXT`（本轮新加） | 只有我们替换过的 `src_gfx_bmpmgr_aarch64.o` |

结论：

- 链接用的游戏主体是 **预编译的 `P1130_GAME_ONLY_GC` / `P1130_GAME_ONLY_HOS_RELRO`**，WaitText、字典 helper 等都在里面；
- `p1286`/`p1446` 这些 Python 模块产出的对象**不会进入最终链接**（之前改 helper 生效，是因为我们直接替换了 `P1446_..._AARCH64.o` 这个预编译文件本身）；
- 隔离目录里的 150 个对象（如 `src_gfx_bmpmgr_aarch64.o`、`src_core_strutil_aarch64.o`、`src_gfx_window_window_text_aarch64.o`）确实会被重新合并，所以对这些文件的替换会生效。

## 三、这条路对后续意味着什么

- 想改 WaitText 的 `setText` 槽：要么直接改 `P1130_GAME_ONLY_*` 这两个预编译对象（二进制补丁/重编不可行），要么在更低层（字体光栅化）统一处理；
- 想改名字绘制：`BmpMgr_DrawTextEx`（隔离对象，可改）与 `Window_DrawText`（隔离对象，可改）是仅有的两个可改入口；
- 字典 helper 的替换方式（直接换 `P1446_..._AARCH64.o`）是可复用的套路。

## 四、当前状态

- 设备：P1116（`ae5d2b73…`），含 `BmpMgr_DrawTextEx` 的 GBK 判定 + `P1461 BMPTEXT` 诊断
- 本轮 p1286 的 setText 改动留在源码里，但对 NRO 无影响（构建结果逐字节相同）
- 字典四件套、存档、剧情资源未动

## 五、下一步（按 P1116 实测结果）

1. 名字变中文 → 收口；
2. 有 `P1461 BMPTEXT gbk=1` 但名字仍乱 → 字体/字形问题；
3. 无 `P1461 BMPTEXT` → 名字走 `P1130` 预编译对象里的 setText 槽，需要改用"字体层自动识别 GBK"的方案（修改可重建的字体对象）或对预编译对象做定点二进制补丁。
